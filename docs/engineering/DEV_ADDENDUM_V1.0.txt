2. 不可妥协的工程原则
2.1 原则一：旧系统作为资产来源，不作为新平台代码底座
fms2026 与 app-android2026 的订单生命周期、运营区域、轨迹、权限、长连接、现场控制和异常处理经验值得继承；但其乘客出行语义、旧数据库、Thymeleaf UI、Android 技术栈和 Zeus 私有协议不能成为新 RaaS 的核心依赖。
正确做法
错误做法
新建 Task/Robot/Capability/Adapter 领域，Legacy 通过映射或 Adapter 接入
将 Car 全局替换为 Robot、Order 全局替换为 Task
先补 Characterization Test，再提取规则或包装协议
边改需求边大规模重构旧代码
新 Schema 与旧数据通过 legacy_id_mapping 对账
直接在旧表中加入大量机器人字段
新 UI 通过新 API；旧 UI 仅在过渡期只读或双写
在 Thymeleaf 页面继续堆多厂商控制逻辑

2.2 原则二：MVP 使用模块化单体，Edge 与 Adapter 独立
13–15 人团队在 27 周内同时交付商用服务和表演两条执行域，首版不应被微服务治理、分布式事务和多套消息系统拖慢。Control Plane 内保持强模块边界；站点网络、厂商 SDK 与本地生命周期不同，因此 Edge/Adapter 必须单独部署、升级和回滚。
2.3 原则三：只发送高层业务意图
允许的云端命令
不得进入通用云端命令
DELIVER / CLEAN / RETURN_TO_DOCK / PAUSE / RESUME / CANCEL
速度、转向角、轮速、电机电流、实时路径点流
START_SHOW / ABORT_SHOW / PRELOAD_ASSET / PREFLIGHT
关节角、力矩、连续步态流、在线生成未知动作
OPEN_COMPARTMENT（在设备/权限支持且通过测试时）
绕过厂商安全回路、急停、避障或本地互锁

2.4 原则四：统一核心能力，保留厂商扩展
能力命名空间
Core Capability ├── navigation ├── delivery ├── cleaning ├── docking ├── compartment ├── elevator └── show  Vendor Extension ├── pudu.* ├── keenon.* ├── unitree.* └── legacy.zeus.*

不支持的能力必须显式返回 CAPABILITY_NOT_SUPPORTED，并记录 Model Profile、固件、Adapter 版本和原因。不得静默忽略，也不得通过 UI 隐藏错误制造“看似成功”。
2.5 原则五：第一条链路必须纵向闭环
所有基础模块都应围绕一条真实可执行路径落地，而不是按“先建完所有表、再做所有页面、最后接机器人”的横向方式推进。纵向闭环通过后，再逐步替换 Simulator 为 PUDU、KEENON、Unitree 或 Legacy Adapter。

4.4 变更规模与 PR 规则
一个 PR 只解决一个业务或工程目标；大规模重构与新功能不得混在同一 PR。
数据库迁移、API/事件变更和 Adapter 行为变化必须在 PR 描述中单独列出，并提供兼容/回滚说明。
新增厂商字段只能存在于对应 Adapter 或 vendor extension；公共 Contract 变化必须有至少两个实现或明确的通用业务理由。
所有 Cursor 生成代码必须经过人工 Review；安全、权限、命令、状态机、数据库迁移和现场控制至少两人审查。
PR 合并前必须通过 required checks；禁止以“后续再补测试”豁免 P0 状态机、幂等、权限和 Adapter TCK。

5.2 Command Envelope
CommandEnvelope v1
{   "commandId": "01J...",   "correlationId": "01J...",   "tenantId": "tenant-001",   "siteId": "site-001",   "robotId": "robot-001",   "commandType": "DELIVERY_START",   "idempotencyKey": "task-10086-attempt-1",   "issuedAt": "2026-08-11T20:00:00Z",   "expiresAt": "2026-08-11T20:02:00Z",   "actor": { "type": "SYSTEM", "id": "scheduler" },   "payload": {} }

要求
行为
幂等
同一 idempotencyKey 在有效窗口内只形成一个可执行厂商命令。
过期
Edge/Adapter 收到 expiresAt 已过的命令必须拒绝，不能“补执行”。
ACK
区分 RECEIVED、ACCEPTED、REJECTED、UNKNOWN；HTTP 200 不等于机器人已开始执行。
租约
同一机器人同一时间只有一个主任务/Show 控制权；租约必须可续期、过期和审计。
撤销
Cancel 是独立命令；必须处理原任务已完成、厂商不支持取消和取消/完成竞态。

5.3 Event Envelope
RobotEvent v1
{   "eventId": "01J...",   "eventType": "TASK_PROGRESS_UPDATED",   "schemaVersion": "1.0",   "tenantId": "tenant-001",   "siteId": "site-001",   "robotId": "robot-001",   "taskId": "task-001",   "sequence": 125,   "occurredAt": "2026-08-11T20:01:10Z",   "receivedAt": "2026-08-11T20:01:12Z",   "source": "PUDU",   "correlationId": "01J...",   "payload": {} }

事件处理必须按 eventId 去重，按 source/robot/sequence 或厂商版本规则识别乱序；业务状态迁移基于允许的状态边，不得用“最后收到的事件覆盖当前状态”。
5.4 Task、Assignment 与 Execution 状态机
状态与对象拆分
Task DRAFT → QUEUED → ASSIGNED → DISPATCHING → RUNNING                                    ├→ SUCCEEDED                                    ├→ FAILED                                    ├→ CANCELED                                    ├→ SUSPENDED                                    └→ NEEDS_INTERVENTION  Task 1 ── N Assignment Assignment 1 ── N ExecutionAttempt ExecutionAttempt 1 ── N Command / Event

不变量
说明
单主执行
同一 Task 同一时刻最多一个 ACTIVE Assignment；同一 Robot 最多一个主控租约。
终态不可回退
SUCCEEDED/FAILED/CANCELED 不得直接回到 RUNNING；恢复必须创建新 Attempt 或新 Task。
业务与设备分离
Task 状态不是 Robot 状态；机器人离线不自动把任务判为 FAILED。
并发安全
取消、完成、超时、人工接管和改派使用版本号/乐观锁和原子状态迁移。
可追踪
每个状态变化记录 source event、actor、reason、correlationId 与时间。

期望行为
